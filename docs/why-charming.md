# Why Charming?

On my programming journey, two tools have shaped me: [Processing](https://processing.org/) and [D3.js](https://d3js.org/). The former makes coding fun, while the latter makes coding elegant. What about Charming? Let's see...

## Inspiration

As I began my journey into computational art, I found [p5.js](https://p5js.org/) and Processing to be excellent starting points. Their artist-centered APIs helped me get things drawn onto the screen quickly and easily, so I could focus on creative expression. I published a series of artworks on [OpenProcessing](https://openprocessing.org/user/144707?view=sketches&o=25), instead of wondering why the computer didn't work as I expected. I also designed [Charming.py](https://github.com/charming-art/charming-py), a creative coding language with the same style of API, for ASCII art in the terminal.

However, when I became a front-end engineer working on visualization, I noticed a shift in programming paradigms, both in visualization grammars and in front-end frameworks: from **imperative** to **declarative**. Declarative grammars speed up development, make it easier to target different platforms, and allow optimizations at the language level. p5.js, the computational art framework for the web, is still imperative, and I found myself using it less and less as I tasted the benefits of declarative programming. So I began to wonder whether a declarative grammar could be designed specifically for computational art and creative coding.

After about two years developing and maintaining version 5.0 of [G2](https://github.com/antvis/G2), I had learned a lot about designing a grammar. I also noticed something visualization and generative art have in common: they are both **data-driven**. Visualization is typically driven by data from daily life, while computational art is driven by data generated by algorithms.

That observation became the foundation of Charming's declarative grammar, and it brought more advantages along the way. A declarative grammar separates the specification (the what) from the execution (the how), which makes code more predictable and lets the same drawing run on different renderers. Charming also borrows the best ideas from G2 and D3.

Later, I also wanted something smaller: plain helpers that take the boilerplate out of SVG, Canvas and HTML, and work alongside D3 and p5 instead of replacing them. That became [Charming API](https://github.com/charming-art/api), the second version of Charming. This version brings both together: Charming 1's declarative language for drawing, and Charming API's helpers.

My hope with Charming is that you spend less time wrangling the machinery of programming and more time "using computing to tell stories". Or put more simply: **with Charming, you'll express more, more easily.**

So how?

## Charming is declarative

Charming's atomic operand is the **flow**: a container that holds data and shapes. A root flow is created by [_cm_.flow](/flow#cm-flow), and its [renderer](/flow#flow-renderer) draws everything appended to it. **Operators** act on flows:

- **[data](/flow#flow-data)** puts data into a flow.
- **[process](/flow#flow-process)** pipes the data through functions that prepare it, such as [_cm_.map](/process#cm-map) and [_cm_.filter](/process#cm-filter).
- **[append](/flow#flow-append)** adds a shape for each datum, computing its attributes from the data. Appending to the result creates nested structures.
- **[transform](/flow#flow-transform)** derives the final attribute values before they reach the renderer, such as [_cm_.mapPosition](/transform#cm-map-position).

Each operator returns a new flow, so operators chain. The relationship between the data and the drawn shapes stays visible in the code. For example, a clover made of circles:

```js eval code=false
(() => {
  const renderer = cm.canvas({width: 640, height: 640});
  const root = cm.flow().renderer(renderer);

  root
    .data(Array.from({length: 120}, (_, i) => (i * Math.PI) / 120))
    .append(cm.circle, {
      x: (t) => Math.cos(t) * Math.cos(t * 3),
      y: (t) => Math.sin(t) * Math.cos(t * 3),
      r: (t) => t,
      fill: "black",
    })
    .transform(cm.mapPosition, {padding: 30})
    .transform(cm.mapAttrs, {r: {range: [8, 15]}});

  root.render();

  return renderer.node();
})();
```

Flows let you organize a sketch in a functional style, as a pipeline from data to shapes, instead of the object-oriented style that Processing and p5.js encourage. The code tends to be shorter and better organized.

## Charming is high performance

The data-driven style gives Charming room for **high performance**. The [WebGL renderer](/webgl) uses [batch rendering](https://developer.mozilla.org/en-US/docs/Web/API/ANGLE_instanced_arrays/drawArraysInstancedANGLE): all the instances of a shape appended together are drawn with one draw call, instead of one call each. Flows group similar shapes together naturally, so this costs nothing extra to write. For the shapes it supports, switching from Canvas to WebGL is a one-line change that lets you draw many more shapes per frame.

Expensive calculations can also move to the GPU. [_cm_.glsl](/webgl#cm-glsl) defines an attribute as a GLSL function, which is compiled into the shader program and evaluated on the GPU for each shape. Interpolated numbers become uniforms, so animating them doesn't recompile anything. GLSL functions also make **shader art** possible: a rect's fill can be a fragment shader. See the [WebGL examples](/webgl).

In the future, a [WebGPU](https://www.w3.org/TR/webgpu/) renderer could go further with compute shaders.

## Charming supports ASCII art

Beyond performance, Charming makes **ASCII art** accessible to artists, designers, educators and beginners. The [terminal renderer](/terminal) draws the same shapes as characters in a grid, positioned in cells and colored with a character, a foreground and a background. It draws into a canvas on the web, using a software rasterizer written in Rust and compiled to WebAssembly.

```js eval code=false
(() => {
  const renderer = cm.terminal({cols: 60, rows: 8});
  const root = cm.flow().renderer(renderer);

  root.append(cm.figlet, {
    text: "Charming",
    x: 30,
    y: 4,
    textAlign: "center",
    textBaseline: "middle",
    fill: () => (x, y, width) => `hsl(${(x / width) * 300}, 90%, 65%)`,
  });

  root.render();

  return renderer.node();
})();
```

## Charming is composable

Inspired by the component philosophy of [React](https://react.dev/), a custom shape in Charming is a pure function. A [composite shape](/shape#composite-shapes) receives a flow and its attribute values, and appends built-in shapes. Here is an arrow:

```js
function arrow(flow, {length, angle, x, y, rotate, ...options}) {
  const group = flow.append(cm.group, {x, y, rotate});
  const l1 = length.map((d) => d / 2);
  const l2 = length.map((d) => -d / 2);
  group.append(cm.link, {x: l2, y: 0, x1: l1, y1: 0, ...options});
  group.append(cm.link, {x: 0, y: 0, x1: l1, y1: 0, rotate: angle, transformOrigin: "end", ...options});
  group.append(cm.link, {x: 0, y: 0, x1: l1, y1: 0, rotate: -angle, transformOrigin: "end", ...options});
}
```

It's used like any built-in shape, and supports transforms too, for example to [draw a flow field](/shape#composite-shapes). Shapes can be as complex as a bar chart with axes, which makes Charming easy to extend.

## Charming is beginner-friendly

Charming offers abstractions such as flows, transforms and scales, but beginners don't need to understand them. They can treat it as syntactic sugar for the [Canvas API](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API), with a plain loop:

```js eval code=false
(() => {
  const renderer = cm.canvas({width: 640, height: 320});
  const root = cm.flow().renderer(renderer);
  for (let i = 0; i < 500; i++) {
    const r = Math.round(Math.random() * 255);
    const g = Math.round(Math.random() * 255);
    const b = Math.round(Math.random() * 255);

    root.append(cm.circle, {
      x: Math.random() * 640,
      y: Math.random() * 320,
      r: Math.random() * 30,
      fill: `rgb(${r}, ${g}, ${b})`,
    });
  }

  root.render();

  return renderer.node();
})();
```

## Compared to p5.js

Charming tries hard to keep the learning curve low, but p5.js remains more accessible to beginners, especially those with no programming experience. p5.js trades that for some issues in larger projects: global functions and state, a large bundle, and the overhead of its Friendly Error System. Charming has no global state: everything is drawn through a flow and its renderer, and the rest are plain functions. So if you're new to programming or JavaScript, p5.js is still the best starting point. Otherwise, Charming is a promising option, and the two can be used together.

## Compared to D3.js

D3 is great, the greatest of all time. Charming works with most of D3's modules, such as [d3-array](https://d3js.org/d3-array), [d3-scale](https://d3js.org/d3-scale) and [d3-scale-chromatic](https://d3js.org/d3-scale-chromatic), and it's encouraged to use them: Charming deliberately doesn't duplicate them. The exception is [d3-selection](https://d3js.org/d3-selection), D3's "renderer". It's built on SVG, which excels at interactive visualization but is less suited to frame-by-frame computational art because of performance. For most visualizations, D3 is the preferred choice. For computational art and performance-sensitive visualizations, Charming may be the better option.

## Charming is close to the platform

SVG and Canvas are two powerful technologies for drawing on the web, but their native APIs take boilerplate. For SVG, you must always specify the namespace:

```js
const ns = "http://www.w3.org/2000/svg";
const svg = document.createElementNS(ns, "svg");
svg.setAttribute("viewBox", "0 0 200 100");
svg.setAttribute("width", "300");
svg.setAttribute("height", "150");
```

For Canvas, you need to handle `devicePixelRatio` to render crisply on every display:

```js
const canvas = document.createElement("canvas");
const ctx = canvas.getContext("2d");
canvas.width = 300 * devicePixelRatio;
canvas.height = 150 * devicePixelRatio;
canvas.style.width = 300 + "px";
canvas.style.height = 150 + "px";
ctx.scale(devicePixelRatio, devicePixelRatio);
```

Many tools in the ecosystem simplify these workflows, but they often add abstractions and features that increase complexity and reduce flexibility. Charming's helpers remove the boilerplate and stay out of the way:

```js
const svg = cm.svg`<svg ${{
  width: 300,
  height: 150,
  viewBox: "0 0 200 100",
}}></svg>`;

const ctx = cm.context2d({width: 300, height: 150});
```

They are data-driven too, in the spirit of [D3](https://d3js.org/), [Observable Plot](https://observablehq.com/plot/) and [AntV G2](https://g2.antv.antgroup.com/):

```js eval code=false
(() => {
  function circles(x, y, r, data = []) {
    if (r < 16) return;
    data.push({x, y, r});
    circles(x - r / 2, y, r * 0.5, data);
    circles(x + r / 2, y, r * 0.5, data);
    circles(x, y - r / 2, r * 0.5, data);
    circles(x, y + r / 2, r * 0.5, data);
    return data;
  }

  return cm.svg`<svg ${{width: 480, height: 480}}>
    <circle ${{
      data: circles(240, 240, 200),
      cx: (d) => d.x,
      cy: (d) => d.y,
      r: (d) => d.r,
      stroke: "black",
      fill: "transparent",
    }}/>
  </svg>`;
})();
```

Each part of Charming does one thing and has a small interface, so you can adopt it piece by piece and plug in your own functions: process functions, transforms, shapes, even renderers.
